# E1 — is the single pool mutex a bottleneck?

Spec §5.4 gates variant B (per-`GOMAXPROCS` sharding) on variant A showing
contention in a `-mutex` or `-block` profile. This is that measurement.

**Status: preliminary null result. Variant B is not justified yet, and the gate
stays open until this is re-run on rig-proxy at its real core count.**

The headline is not the one the spec expected: the pool mutex is not what the
pool spends its time on. `time.Now` is.

## Numbers

`go test ./internal/upstream -bench . -benchtime 2s -count 3 -cpu 8`,
Apple M3, darwin/arm64, GOMAXPROCS=8. Median of 3, all runs 0 allocs/op.

| Benchmark | ns/op | What it says |
|---|---|---|
| `AcquireReleaseUncontended` | **71.4** | one goroutine, warm pool: the floor |
| `AcquireReleaseCoarseClock` | **11.8** | same, with a zero-cost clock |
| `AcquireReleaseContended/hold=0` | **250.9** | 8 goroutines, pathological |
| `MutexOnlyContended` (control) | **249.1** | 8 goroutines, bare mutex, empty section |
| `AcquireReleaseContended/hold=1µs` | 670.7 | 8 goroutines, realistic-ish hold |
| `ColdDial` | 56.9 | the dial path, for contrast |

## Reading 1 — the clock costs 5× what the pool does

71.4ns → 11.8ns when `Config.Now` returns a constant. **83% of the pool's
uncontended per-request cost is two `time.Now` calls**, one in `Acquire` to age
out expired entries and one in `Release` to stamp the returned connection. The
lock, the slice manipulation and the counters together are 11.8ns.

This is the actionable result of E1, and it is not about sharding at all. The
fix needs no new code here: `Config.Now` is already the injection point, so the
proxy can pass a coarse cached time updated once per event-loop pass. NGINX
caches its clock for exactly this reason. On Linux `time.Now` is a vDSO
`clock_gettime` at roughly 20-25ns rather than the ~30ns measured here, so the
ratio will be smaller on the rig — but the clock will still dominate.

One clock-related fix already applied: `Release` used to call `p.now()` *inside*
the critical section, which put ~30ns of clock into a section whose real work is
~6ns. It now reads the clock before taking the lock. Had that stayed, E1 would
have been measuring `time.Now` under contention and concluded the mutex was hot.

## Reading 2 — under contention the pool is indistinguishable from a bare mutex

`AcquireReleaseContended/hold=0` at 250.9ns and `MutexOnlyContended` at 249.1ns
are the same number. That is what the control was for: at full contention the
pool's own bookkeeping is free, and 100% of the cost is the lock. Sharding is
therefore the *only* thing that could help — there is no cheaper critical
section to write.

So the question reduces to arithmetic: does the ceiling matter?

250ns/op at 8 cores = **4.0M pool operations/sec**, and one request is one
operation. W1 drives 50k RPS (`workload.go`). Even a peak-RPS run on this class
of hardware is unlikely to reach 1M. The ceiling is 4-80× above the operating
range, at the *pathological* hold of zero — a real request holds its connection
for an origin round trip, during which the lock is free for everyone else.

## The profiles, and how not to misread them

`-mutexprofile` and `-blockprofile` over `hold=1µs`:

```
Type: delay
 3668.43ms 82.71%  sync.(*Mutex).Unlock (inline)
  766.84ms 17.29%  runtime.unlock (inline)
         0     0%  ...upstream.(*Pool).Acquire   (cum 48.90%)
         0     0%  ...upstream.(*Pool).Release   (cum 48.52%)
```

```
Type: delay (block)
     4.61s 27.45%  sync.(*Mutex).Lock (inline)
```

Two things to say about this before anyone points at the red and starts building
variant B:

1. **`Unlock` is not slow.** Go's mutex profile attributes the delay at unlock
   time — the holder is charged for the wait it caused others. This is how every
   contended Go mutex looks; it is not a finding.
2. **This benchmark is 8 goroutines doing nothing but pool operations.** Its
   contention is by construction, not by discovery. A profile of the *proxy*
   under W1 is the one that gates variant B, because there each goroutine spends
   its time parsing, writing and relaying, and touches the pool twice.

A synthetic benchmark can prove the ceiling is high enough. It cannot prove
contention exists in production, and this one does not try to.

## What would change the verdict

- **Core count.** This is 8 cores. rig-proxy is a `.metal` or whole-socket
  instance, and contention on a single cache line worsens faster than linearly
  with core count. The 4.0M ceiling is an 8-core number and does not transfer.
- **Realised RPS.** If peak-RPS runs land within ~5× of the measured ceiling,
  the gate opens.
- **A `-mutex` profile of the running proxy** under W1 showing
  `upstream.(*Pool).Acquire` or `.Release` as a significant site. That is the
  spec's stated gate and it has not been run yet.

Until then variant A stands, and the recorded null result is the finding.

## Reproducing

```sh
make e1          # timings, then profiles, then the top frames of each
```

Timings and profiles are captured in separate runs on purpose: profiling
perturbs the thing being timed. The same `hold=1µs` case measured 670ns clean
and 419ns under the profiler, which is reason enough not to read timings off a
profiled run.
